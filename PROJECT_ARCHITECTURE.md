## 1. System Overview

### 1.1 Problem Statement

VFSTR currently has no automated, continuously updated record of faculty research output. The annual process of emailing faculty for publication lists produces incomplete, inconsistent, and unverifiable data. This system replaces that process with an **agentic AI pipeline** that automatically discovers, reconciles, verifies, enriches, monitors, and reports institutional research output.

### 1.2 Core Design Principle

```
DATA SOURCES → SOURCE CONNECTORS → DISCOVERY AGENTS → NORMALIZATION
→ IDENTITY RESOLUTION → PUBLICATION MATCHING → DEDUPLICATION
→ AUTHOR ATTRIBUTION → METADATA ENRICHMENT → QUALITY/RISK ANALYSIS
→ VERIFICATION + CONFIDENCE SCORING → HUMAN REVIEW WHEN REQUIRED
→ VERIFIED RESEARCH RECORD → HISTORICAL METRICS
→ REPORTING / ACCREDITATION EVIDENCE → CONTINUOUS MONITORING
```

This is NOT "upload CSV → AI → dashboard." Every record carries provenance, confidence scores, and evidence chains.

### 1.3 Primary Users

| Role | Access Scope | Key Capabilities |
|------|-------------|-------------------|
| **Faculty** | Own profile + publications | View, confirm, correct, add publications |
| **Department Admin / HOD** | Department-wide | Department monitoring, review queues, reports |
| **Research Admin / Dean** | Institution-wide | All analytics, verification, accreditation evidence |
| **Quality Assurance Cell** | Institution-wide (read) | Audit trails, compliance reports, flagged records |

| **Database** | PostgreSQL 16 | ACID, JSONB, full-text search, production-grade |
| **Vector Search** | pgvector extension | Semantic similarity without extra infrastructure |
| **Migrations** | Alembic | Versioned schema evolution |
| **ORM** | SQLAlchemy 2.0 (async) | Async support, type annotations |
| **Background Jobs** | Celery + Redis | Reliable scheduled ingestion, task monitoring |
| **Data Validation** | Pydantic v2 | Strict schemas at every boundary |
| **Data Processing** | Pandas + custom pipelines | CSV ingestion, normalization, deduplication |
| **Authentication** | JWT + bcrypt | Stateless, role-based |
| **API Documentation** | OpenAPI (auto-generated by FastAPI) | Always up-to-date |
| **Containerization** | Docker + Docker Compose | Reproducible local + deployment |

| `/agents` | `GET /status`, `GET /runs`, `GET /logs` | Admin |
| `/assistant` | `POST /query` (natural language) | All authenticated |

```
                                     └──────────┬───────────┘

                                     ┌──────────▼───────────┐
                                     │    PostgreSQL         │
                                     │  (Result Backend)     │
                                     └──────────────────────┘
```

**Scheduled Tasks**:
- `sync_all_sources` — Full discovery cycle (configurable: daily/weekly)
- `update_citation_snapshots` — Citation count refresh (weekly)
- `compute_metrics` — h-index, i10-index recalculation (after citation update)
- `generate_alerts` — New discovery/conflict alerts (after sync)
- `cleanup_stale_runs` — Housekeeping (daily)

### 5.2 Security Controls

| Control | Implementation |
|---------|---------------|
| **Secrets** | `.env` files, never committed; `python-dotenv` / `pydantic-settings` |
| **API Keys** | Environment variables for Groq, OpenAlex email, research APIs |
| **Password Storage** | bcrypt with salt |
| **JWT** | RS256 or HS256, short-lived access (15min), refresh (7d) |
| **Input Validation** | Pydantic v2 on all API boundaries |
| **CORS** | Whitelist frontend origin only |
| **Rate Limiting** | slowapi on public endpoints |
| **Audit Log** | Every human decision, agent run, data modification logged with timestamp + actor |
| **Evidence Integrity** | Provenance records are append-only, never silently modified |

### 6.1 Synchronization Cycle

```
┌──────────────────┐
│  Celery Beat      │  ◄── Configurable schedule (cron)
│  Scheduler        │
└────────┬─────────┘
         │ triggers
         ▼
┌──────────────────┐    ┌─────────────────┐    ┌──────────────────┐

└──────────────────┘    └─────────────────┘    └────────┬─────────┘
                                                        │
┌──────────────────┐    ┌─────────────────┐    ┌────────▼─────────┐
│ 6. Enrich        │◀───│ 5. Attribute    │◀───│ 4. Deduplicate   │
│    Metadata      │    │    Faculty      │    │    & Match       │
└────────┬─────────┘    └─────────────────┘    └──────────────────┘
         │
┌────────▼─────────┐    ┌─────────────────┐    ┌──────────────────┐
│ 7. Risk/Integrity│───▶│ 8. Verify &     │───▶│ 9. Update DB +   │
│    Analysis      │    │    Score        │    │    Metrics        │
└──────────────────┘    └─────────────────┘    └────────┬─────────┘
                                                        │
                                               ┌────────▼─────────┐
                                               │ 10. Generate     │
                                               │     Alerts/Tasks │
                                               └──────────────────┘
```

### 6.2 Schedule Configuration

```python
# Configurable via environment or admin UI
SYNC_SCHEDULES = {
    "full_discovery": "0 2 * * 0",      # Weekly at 2 AM Sunday
    "citation_refresh": "0 3 * * 3",     # Weekly at 3 AM Wednesday
    "metrics_compute": "0 4 * * 3",      # After citation refresh
    "alert_generation": "0 5 * * *",     # Daily at 5 AM
    "report_generation": "0 6 1 * *",    # Monthly on 1st
}
```

The architecture supports changing schedules at runtime without code changes.

## 7. AutoResearch Integration Strategy

### 7.1 Existing AutoResearch Capabilities

The AutoResearch Agent project provides:

| Agent | Capability | Integration Potential |
|-------|-----------|----------------------|
| Search Agent | ArXiv + Semantic Scholar search | **HIGH** — Reusable as discovery connector |
| Extraction Agent | LLM-powered paper analysis | **MEDIUM** — Useful for metadata enrichment |
| Gap Agent | Research gap identification | **MEDIUM** — Faculty research profile enrichment |
| Contradiction Agent | Cross-paper contradiction detection | **LOW** — Not core to monitoring |
| Trend Agent | Research trend prediction | **MEDIUM** — Institutional trend intelligence |
| Review Agent | Literature review generation | **LOW** — Not core to monitoring |
| Hypothesis Agent | Hypothesis generation | **LOW** — Not core to monitoring |
| Chatbot Agent | Q&A over research data | **HIGH** — Foundation for Research Assistant |

### 7.2 Integration Approach

```
Phase 16: AutoResearch Integration
│
├── EXTRACT: Refactor connectors (ArXiv, Semantic Scholar)
│   └── Wrap as backend/app/connectors/ implementations
│
├── ADAPT: Paper analysis capabilities
│   └── Use extraction/trend agents within enrichment pipeline
│
├── EXTEND: Chatbot → Research Intelligence Assistant
│   └── Adapt to query verified institutional data instead of ad-hoc papers
│
└── CLEAN API: All integration via backend service layer
    └── Never import AutoResearch code directly into agents
```

> [!WARNING]
> AutoResearch uses Groq/llama-3.1-8b-instant. Our system must support provider abstraction (Groq, OpenAI, local models) so the LLM can be swapped based on institutional requirements.

## 8. Deployment Architecture

### 8.1 Docker Compose (Development + Demo)

```yaml
services:
  postgres:     # PostgreSQL 16 + pgvector
  redis:        # Message broker for Celery
  backend:      # FastAPI application
  celery-worker: # Background task workers
  celery-beat:  # Scheduled task scheduler
  frontend:     # Vite dev server / Nginx (production)
```

### 8.2 Production Considerations

- PostgreSQL: Managed instance (Cloud SQL, RDS, or institutional server)
- Redis: Managed or containerized
- Backend: Multiple FastAPI workers behind Nginx/Gunicorn
- Frontend: Static build served by Nginx or CDN
- HTTPS: Required for all production traffic
- Backups: PostgreSQL WAL archiving + daily snapshots
